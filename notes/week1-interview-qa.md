# Week 1 项目面试问答

## 1. 为什么在这个项目里使用异步请求？

LLM 请求的主要耗时通常是等待网络和模型推理，这是 IO 密集型工作。同步执行多个互不依赖的请求时，程序需要等待上一个响应后再开始下一个；异步调用可以在一个请求等待 IO 时让事件循环运行其他请求。我用 `httpx.AsyncClient` 和 `asyncio.gather()` 并发调用多个 prompt，并比较总耗时。异步优化的是 IO 等待，不等于多线程，也不会自动加速 CPU 密集型计算。

## 2. 为什么选择 httpx 而不是 requests？

项目需要同步调用，也需要 asyncio 异步并发。httpx 同时提供 `httpx.Client` 和 `httpx.AsyncClient`，可以使用相近的请求接口完成这两类工作。它还有明确的 timeout 配置和可 mock 的 HTTP 调用边界，便于异常分类和单元测试。

## 3. API Key 如何保护？

API Key 放在本地 `.env`，由 `python-dotenv` 读取；`.env` 应由 `.gitignore` 排除，仓库只提供不含真实凭证的 `.env.example`。请求只通过 `Authorization: Bearer ...` 发送，配置对象的 `repr` 对 Key 做掩码，避免意外出现在终端或日志中。测试使用假 Key，不需要真实凭证。

## 4. 为什么设计分层异常？

网络失败、超时、认证失败、限流、模型错误和响应格式错误的修复方式不同。将它们表示为不同异常后，CLI 可以对网络问题提示重试、对认证问题停止请求；测试也能明确断言特定响应状态会映射到预期异常，而不是只检查某个通用异常。

## 5. 这个项目的工程亮点和当前局限是什么？

工程亮点是职责拆分、同步/异步请求共享构建与解析逻辑、历史持久化、分类错误处理，以及使用 `tmp_path` 和 mock 编写无需联网的测试。当前局限是历史仍使用本地 JSON，缺少多用户和并发写入保证；异步客户端生命周期也仍以单次请求为主。后续可以在 Web 服务场景中迁移数据库、管理长生命周期的 AsyncClient，并补充 CI 和集成测试。
